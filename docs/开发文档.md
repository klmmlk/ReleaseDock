# 多软件升级分发系统 开发文档

项目名称:发布坞/ReleaseDock
版本：v0.1  
目标：基于 Cloudflare Workers + R2 + D1，提供一个支持多软件接入的“版本查询 + Changelog + 文件下载 + 发布管理”系统。  
范围：不包含具体代码实现，只定义架构、数据模型、接口契约、发布流程与客户端集成约定。

---

## 1. 系统概述

### 1.1 核心能力

- 多软件共用一套基础设施，通过 `app_id` 隔离。
- 客户端查询指定软件、指定通道的最新版本。
- 服务端根据客户端当前版本，自动拼接中间版本的 Changelog。
- 更新包存放在 R2，通过 Worker 受控下载，R2 桶不公开。
- 开发者通过管理 API 完成“登记版本”和“上线版本”，支持回滚与灰度。
- 客户端集成成本低：只需配置固定查询地址、当前版本号和 `client_id`。

### 1.2 组件职责

| 组件 | 职责 |
| :--- | :--- |
| Cloudflare Workers | API 网关、版本查询、Changelog 拼接、下载路由、管理接口、灰度分流 |
| Cloudflare R2 | 存放各软件的更新包/安装包，按 `app_id/channel/version/` 前缀组织 |
| Cloudflare D1 | 存放应用、版本、通道指针、发布状态、Changelog、灰度配置等元数据 |
| Cloudflare Access（建议） | 保护管理接口，限制只有内部人员或 CI 可访问 |

### 1.3 非目标

- 不实现 P2P 分发。
- 不实现内容寻址。
- 不要求客户端安装额外运行时。
- 初期不建设完整 Web 管理后台，管理接口 + 脚本/CI 即可。

## 2. 总体架构

客户端请求流程：

1. 客户端启动或定时触发，向版本查询接口发起请求。
2. 请求携带：`app_id`、`channel`、`current_version`、`client_id`。
3. Worker 查询 D1：
   - 找到该 `app_id + channel` 的当前生效版本指针。
   - 判断是否有更新。
   - 判断是否强制更新。
   - 根据灰度配置决定该 `client_id` 是否可见新版本。
   - 拼接从 `current_version` 之后到最新版本的 Changelog。
4. Worker 返回更新清单 JSON。
5. 客户端如需更新，请求下载接口。
6. Worker 从 R2 流式返回文件。
7. 客户端下载完成后用 `sha256` 校验，再交给安装逻辑。

发布流程：

1. 开发者/CI 上传文件到 R2，获得对象键。
2. 调用“登记版本”接口，写入 D1，状态为 `draft`。
3. 确认无误后调用“上线版本”接口，将通道指针指向该版本。
4. 客户端下一次查询即可看到新版本。
5. 如需回滚，将通道指针指回旧版本即可，无需重新上传文件。

## 3. 数据模型

以下为逻辑字段定义，不限定具体 SQL 实现。

### 3.1 应用表 `apps`

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `app_id` | 字符串，主键 | 全局唯一应用标识，如 `com.yourco.product-a` |
| `name` | 字符串 | 展示名称 |
| `status` | 枚举 | `active` / `disabled` |
| `created_at` | 时间 | 创建时间 |
| `updated_at` | 时间 | 更新时间 |

### 3.2 版本表 `releases`

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | 字符串，主键 | 发布记录 ID |
| `app_id` | 字符串 | 关联应用 |
| `channel` | 字符串 | 通道，如 `stable` / `beta` |
| `version` | 字符串 | 语义化版本号，如 `1.3.0` |
| `r2_key` | 字符串 | R2 对象键，如 `product-a/stable/1.3.0/setup.exe` |
| `sha256` | 字符串 | 文件 SHA-256 |
| `size` | 整数 | 文件字节数 |
| `changelog` | 文本/JSON | 该版本变更说明，建议 Markdown 或结构化条目 |
| `status` | 枚举 | `draft` / `live` / `archived` |
| `rollout` | 整数 | 灰度百分比，0–100，默认 100 |
| `created_at` | 时间 | 登记时间 |
| `promoted_at` | 时间 | 上线时间 |
| `created_by` | 字符串 | 操作者标识，可选 |

约束建议：

- 同一 `app_id + channel + version` 唯一。
- `status = live` 的记录不直接删除，回滚通过移动指针实现。
- 文件一旦上线，不建议覆盖同一 `r2_key`；新版本应使用新对象键。

### 3.3 通道指针表 `app_channels`

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `app_id` | 字符串 | 应用标识 |
| `channel` | 字符串 | 通道 |
| `current_release_id` | 字符串 | 当前生效版本记录 ID |
| `min_supported_version` | 字符串 | 低于该版本强制更新 |
| `updated_at` | 时间 | 更新时间 |

主键建议：`app_id + channel`。

说明：

- “上线”本质是把 `current_release_id` 指向某个 `release`。
- “回滚”本质是把 `current_release_id` 指回旧 `release`。
- `min_supported_version` 由服务端控制强制更新，不依赖客户端判断。

### 3.4 审计表 `audit_logs`（建议）

| 字段 | 说明 |
| :--- | :--- |
| `id` | 日志 ID |
| `action` | `register_release` / `promote` / `rollback` / `update_min_version` |
| `app_id` | 应用 |
| `channel` | 通道 |
| `release_id` | 相关版本 |
| `operator` | 操作者 |
| `created_at` | 时间 |
| `detail` | 变更详情 |

## 4. API 契约

### 4.1 通用约定

- 所有接口使用 HTTPS。
- 请求与响应均为 JSON，下载接口除外。
- 时间使用 ISO 8601 UTC。
- 管理接口必须鉴权，建议同时启用 Cloudflare Access 与 Bearer Token。
- 客户端接口不要求登录，但可要求携带 `client_id`。
- 错误响应统一格式：

```json
{
  "error": {
    "code": "RELEASE_NOT_FOUND",
    "message": "指定版本不存在"
  }
}
```

### 4.2 版本查询

`GET /v1/updates/{app_id}/{channel}`

查询参数：

| 参数 | 必填 | 说明 |
| :--- | :--- | :--- |
| `current` | 是 | 客户端当前版本号 |
| `client_id` | 建议 | 客户端唯一标识，用于灰度分流；可由客户端首次启动生成并持久化 |
| `os` | 可选 | 操作系统标识，预留 |
| `arch` | 可选 | 架构标识，预留 |
| `include_changelog` | 可选 | 默认 `true` |

响应示例：

```json
{
  "app_id": "com.yourco.product-a",
  "channel": "stable",
  "update_available": true,
  "latest": "1.5.0",
  "current": "1.2.0",
  "mandatory": false,
  "min_supported_version": "1.0.0",
  "download_url": "https://update.yourdomain.com/v1/download/rel_abc123",
  "sha256": "abc123...",
  "size": 12345678,
  "changelog": [
    {
      "version": "1.3.0",
      "items": ["修复登录超时问题", "优化启动速度"]
    },
    {
      "version": "1.4.0",
      "items": ["新增离线模式"]
    },
    {
      "version": "1.5.0",
      "items": ["升级数据库结构，需重启完成"]
    }
  ],
  "published_at": "2026-10-20T08:00:00Z"
}
```

无更新时：

```json
{
  "app_id": "com.yourco.product-a",
  "channel": "stable",
  "update_available": false,
  "latest": "1.2.0",
  "current": "1.2.0",
  "mandatory": false
}
```

行为规则：

1. 查询 `app_channels` 得到当前生效 `release`。
2. 若 `current` 等于最新版本，返回 `update_available = false`。
3. 若 `current` 低于 `min_supported_version`，返回 `mandatory = true`。
4. 若当前生效版本配置了灰度 `rollout < 100`：
   - 对 `client_id` 做稳定哈希，映射到 0–99。
   - 若哈希值大于等于 `rollout`，则对该客户端视为“无更新”，返回当前已上线旧版本信息。
   - 无 `client_id` 时，默认不进入灰度，返回旧版本。
5. Changelog 拼接：
   - 找出 `current` 之后、最新版本及之前的所有 `live` 版本。
   - 按版本从旧到新排序。
   - 最多拼接 5 个版本；超过时只保留最近 5 个，并在响应中增加 `changelog_truncated = true`。
   - 若 `current` 在 D1 中找不到，不报错，只返回最新版本的 Changelog。
   - 若 `include_changelog = false`，不返回 `changelog` 字段。

缓存建议：

- 查询接口可设置较短缓存，如 60 秒。
- 管理接口不缓存。
- 下载接口可设置较长缓存，但 URL 中应包含不可变版本标识。

### 4.3 文件下载

`GET /v1/download/{release_id}`

行为：

1. 根据 `release_id` 查询 D1。
2. 仅允许下载 `status = live` 或 `status = archived` 的记录；`draft` 不允许下载。
3. 从 R2 读取对象并流式返回。
4. 响应头建议包含：
   - `Content-Length`
   - `Content-Type: application/octet-stream`
   - `ETag`
   - `X-Checksum-Sha256`
5. 可选鉴权：
   - 初期可不鉴权，依赖不可预测的 `release_id` 和 HTTPS。
   - 若需要更强控制，可在查询响应中下发短时效签名 URL，下载接口校验签名。

### 4.4 管理接口：登记版本

`POST /v1/admin/releases`

鉴权：`Authorization: Bearer <ADMIN_TOKEN>`，并建议启用 Cloudflare Access。

请求示例：

```json
{
  "app_id": "com.yourco.product-a",
  "channel": "stable",
  "version": "1.5.0",
  "r2_key": "product-a/stable/1.5.0/setup.exe",
  "sha256": "abc123...",
  "size": 12345678,
  "changelog": "## 1.5.0\n- 升级数据库结构\n- 修复登录超时",
  "rollout": 100
}
```

响应示例：

```json
{
  "release_id": "rel_abc123",
  "status": "draft",
  "message": "版本已登记，尚未上线"
}
```

规则：

- 登记后状态为 `draft`，客户端查询不到。
- 同一 `app_id + channel + version` 不可重复登记。
- 文件应先上传至 R2，再登记；登记时不校验文件内容，只记录元数据。
- 建议在登记时校验 `sha256` 格式和 `size > 0`。

### 4.5 管理接口：上线版本

`POST /v1/admin/releases/{release_id}/promote`

请求示例：

```json
{
  "expected_current_release_id": "rel_old123",
  "reason": "正式发布 1.5.0"
}
```

响应示例：

```json
{
  "app_id": "com.yourco.product-a",
  "channel": "stable",
  "current_release_id": "rel_abc123",
  "message": "已上线"
}
```

规则：

- 只有 `draft` 或 `archived` 的版本可被上线。
- 上线操作将 `app_channels.current_release_id` 指向该版本，并将该版本状态置为 `live`。
- 旧版本状态可置为 `archived`，但保留记录以支持回滚。
- `expected_current_release_id` 用于乐观并发控制：若当前指针已变化，则拒绝，避免多人同时发布互相覆盖。
- 上线后客户端查询即可见。

### 4.6 管理接口：回滚

`POST /v1/admin/releases/{release_id}/rollback`

语义：将通道指针指回指定的旧版本。

请求示例：

```json
{
  "expected_current_release_id": "rel_abc123",
  "reason": "1.5.0 出现严重崩溃，回滚到 1.4.0"
}
```

响应示例：

```json
{
  "app_id": "com.yourco.product-a",
  "channel": "stable",
  "current_release_id": "rel_old456",
  "message": "已回滚"
}
```

规则：

- 目标版本必须属于同一 `app_id + channel`。
- 目标版本状态可为 `live` 或 `archived`。
- 回滚后，目标版本状态置为 `live`，原当前版本置为 `archived`。
- 不删除文件，不重新上传。

### 4.7 管理接口：更新强制更新阈值

`PATCH /v1/admin/apps/{app_id}/channels/{channel}`

请求示例：

```json
{
  "min_supported_version": "1.3.0"
}
```

说明：

- 客户端版本低于该值时，查询响应返回 `mandatory = true`。
- 该字段由服务端控制，客户端不得自行决定强制更新。

### 4.8 管理接口：查询版本列表

`GET /v1/admin/releases?app_id=com.yourco.product-a&channel=stable&status=live`

返回版本列表，供发布脚本确认当前状态、选择回滚目标。

## 5. Changelog 规范

### 5.1 存储建议

- 每个版本独立保存自己的 Changelog。
- 推荐使用 Markdown 文本，客户端可自行渲染。
- 若客户端不便渲染 Markdown，可使用结构化数组：

```json
[
  "修复登录超时问题",
  "优化启动速度"
]
```

### 5.2 拼接规则

- 查询时由服务端拼接，客户端不自行拼接。
- 从 `current` 之后到最新版本，按版本升序排列。
- 最多拼接 5 个版本。
- 若超过 5 个，只保留最近 5 个，并返回 `changelog_truncated = true`。
- 若 `current` 不存在，只返回最新版本 Changelog。
- 若 `current` 等于最新版本，不返回 Changelog。

### 5.3 客户端展示建议

- 普通更新：展示拼接后的完整 Changelog。
- 强制更新：优先展示 `min_supported_version` 和关键 breaking change。
- 大跨度升级：若 `changelog_truncated = true`，提示“仅展示最近 5 个版本的更新说明”。

## 6. 灰度与强制更新

### 6.1 灰度发布

- 在 `releases.rollout` 中配置 0–100。
- Worker 根据 `client_id` 稳定哈希取模 100。
- 哈希值小于 `rollout` 的客户端可见新版本，否则返回旧版本信息。
- 客户端无需感知灰度逻辑，只看到“有更新/无更新”。
- 无 `client_id` 的请求默认不进入灰度，返回旧版本。
- 灰度比例可随时调整，无需重新发版。

建议：

- 首次灰度从 5% 或 10% 开始。
- 观察错误率和崩溃率后逐步提升。
- 灰度期间保留一键回滚能力。

### 6.2 强制更新

- 强制更新由服务端 `min_supported_version` 决定。
- 当 `current < min_supported_version` 时，返回 `mandatory = true`。
- 不建议把“每次版本不一致”都设为强制更新。
- 客户端收到 `mandatory = true` 后，应阻止继续使用旧版本，引导下载。

## 7. 开发者发布流程

### 7.1 标准流程

1. 构建产物，计算 SHA-256。
2. 上传文件到 R2，对象键建议：
   `{app_id}/{channel}/{version}/{filename}`
3. 调用“登记版本”接口，提交元数据与 Changelog。
4. 在测试环境用 `channel = beta` 验证。
5. 调用“上线版本”接口，将 `stable` 通道指针指向新版本。
6. 观察客户端更新情况与错误率。
7. 如需回滚，调用“回滚”接口。

### 7.2 CI 集成建议

- 将“登记”和“上线”封装为两个 CI 步骤。
- 登记步骤可在每次构建时自动执行。
- 上线步骤建议手动触发或增加审批。
- 管理 Token 存放在 CI Secret 中，不写入代码仓库。
- 建议记录每次发布的 `release_id` 到构建日志。

### 7.3 发布检查清单

- [ ] 文件已上传 R2，且 `sha256` 与构建产物一致
- [ ] 版本号符合语义化版本规范
- [ ] Changelog 已填写，包含 breaking change
- [ ] 已在 beta 通道验证
- [ ] 灰度比例已设置
- [ ] `min_supported_version` 是否需要调整
- [ ] 回滚目标版本已确认

## 8. 客户端集成规范

### 8.1 客户端配置

每个软件只需配置：

| 配置项 | 示例 | 说明 |
| :--- | :--- | :--- |
| `base_url` | `https://update.yourdomain.com` | 统一服务地址 |
| `app_id` | `com.yourco.product-a` | 应用标识 |
| `channel` | `stable` | 通道 |
| `current_version` | `1.2.0` | 当前版本 |
| `client_id` | 持久化 UUID | 首次启动生成并保存 |

查询地址拼接规则：

`{base_url}/v1/updates/{app_id}/{channel}?current={current_version}&client_id={client_id}`

### 8.2 检查时机

- 软件启动后异步检查一次，不阻塞主流程。
- 之后每 6 小时后台静默检查一次。
- 用户手动点击“检查更新”时立即检查。
- 不要在主界面加载时同步等待更新接口。

### 8.3 客户端处理流程

1. 发起查询请求。
2. 若 `update_available = false`，结束。
3. 若 `update_available = true`：
   - 展示 Changelog。
   - 若 `mandatory = true`，提示必须更新。
   - 否则允许用户稍后更新。
4. 用户确认后，请求 `download_url`。
5. 下载完成后计算 SHA-256，与响应中的 `sha256` 比对。
6. 校验失败则删除临时文件并提示重试。
7. 校验通过后交给安装逻辑。
8. 安装完成后更新本地 `current_version`。

### 8.4 错误处理

- 网络失败：静默重试，不打扰用户。
- 查询接口 5xx：按无更新处理，下次再试。
- 下载中断：支持断点续传或重新下载。
- SHA-256 不匹配：视为下载损坏，重试一次；仍失败则提示联系支持。
- 强制更新下载失败：提供备用下载地址或提示检查网络。

### 8.5 多软件复用

- 所有软件共用同一套客户端更新库。
- 差异仅在于 `app_id`、`channel`、`current_version` 和安装逻辑。
- 更新库不包含业务逻辑，只负责查询、下载、校验、回调。
- 安装阶段通过回调交给各软件自己的安装器。

## 9. 安全设计

### 9.1 管理接口

- 必须使用 HTTPS。
- 必须校验 `Authorization: Bearer <ADMIN_TOKEN>`。
- 建议同时启用 Cloudflare Access，限制来源邮箱或服务令牌。
- Token 定期轮换，存放在 Secret 管理服务中。
- 管理接口不缓存，响应头设置 `Cache-Control: no-store`。

### 9.2 下载接口

- R2 桶不公开，只允许 Worker 绑定访问。
- 下载 URL 使用 `release_id`，不使用可猜测的路径。
- 可选：查询响应中下发短时效签名 URL，下载接口校验签名与过期时间。
- 响应头返回 `X-Checksum-Sha256`，客户端必须校验。

### 9.3 数据完整性

- 登记版本时记录 `sha256` 和 `size`。
- 客户端下载后必须校验 `sha256`。
- 上线前建议人工或 CI 校验 R2 文件哈希与登记值一致。

### 9.4 防滥用

- 对查询接口按 IP 或 `client_id` 做速率限制。
- 对下载接口可做并发限制。
- 监控异常下载量，防止流量盗刷。
- 管理接口失败登录记录审计日志。

## 11. 缓存与性能

- 查询接口：`Cache-Control: public, max-age=60`。
- 下载接口：`Cache-Control: public, max-age=31536000, immutable`，因为 URL 含不可变 `release_id`。
- 管理接口：`Cache-Control: no-store`。
- Changelog 拼接在 Worker 内完成，数据量小，避免多次往返 D1。
- 下载使用 R2 流式响应，避免 Worker 内存占用过高。
- 对热门版本可依赖 Cloudflare 边缘缓存降低 R2 回源。

## 12. 监控与运维

建议监控指标：

- 查询接口 QPS、P95 延迟、错误率。
- 下载接口流量、失败率、平均下载耗时。
- 各 `app_id + channel` 当前版本分布。
- 强制更新触发次数。
- 管理接口调用记录与失败次数。
- R2 存储用量与出口流量。
- D1 查询延迟与错误率。

建议告警：

- 查询接口错误率持续超过阈值。
- 下载失败率异常升高。
- 管理接口鉴权失败次数异常。
- 某个应用长时间无查询请求（可能客户端配置错误）。

## 13. 实施里程碑

### 阶段一：最小可用

- 建立 D1 表结构。
- 实现查询接口、下载接口。
- 实现登记版本、上线版本两个管理接口。
- 接入第一个软件，跑通“查询 → 下载 → 校验 → 安装”。
- 管理接口用静态 Token + Cloudflare Access 保护。

### 阶段二：多软件验证

- 接入第二个软件。
- 验证 `app_id` 隔离、Changelog 拼接、下载路径复用。
- 补齐错误码、审计日志、基础监控。
- 封装客户端更新库，减少重复集成成本。

### 阶段三：发布治理

- 增加灰度发布。
- 增加强制更新阈值管理。
- 增加回滚接口与发布检查清单。
- 将发布流程接入 CI。
- 根据流量情况评估缓存策略与速率限制。

### 阶段四：可选增强

- 管理后台或内部发布看板。
- 下载短时效签名 URL。
- 按 OS/架构分发不同安装包。
- 发布审批流。
- 更细粒度的审计与告警。

## 14. 关键设计决策摘要

| 决策 | 结论 |
| :--- | :--- |
| 基础设施 | Workers + R2 + D1 |
| 多软件隔离 | 通过 `app_id` 字段，不额外部署 |
| 发布模型 | 登记与上线分离 |
| 回滚 | 移动通道指针，不重新上传 |
| Changelog | 每版本独立存储，查询时服务端拼接，最多 5 条 |
| 强制更新 | 由服务端 `min_supported_version` 判断 |
| 灰度 | 服务端按 `client_id` 哈希分流，客户端无感 |
| 客户端集成 | 固定查询地址 + 当前版本 + `client_id` |
| 完整性校验 | 客户端下载后校验 SHA-256 |
| 安全 | 管理接口 Token + Cloudflare Access；R2 不公开 |

### 15.1 阶段一实现补充口径（2026-10-20）

- 新增 `POST /v1/admin/apps`、`GET /v1/admin/apps`：文档原未定义应用管理接口，但登记版本依赖应用存在，接入新应用必需。
- Changelog 拼接范围取**所有已发布版本（live + archived）**：因上线流程会将旧版本置为 `archived`，仅查 `live` 会使多版本拼接失效。
- 新增错误码 `R2_OBJECT_NOT_FOUND`（404）：上线前校验 R2 对象存在，防止把缺文件的版本推上线。
- 灰度随阶段一实现：`client_id` 做 SHA-256 稳定哈希对 100 取模，未命中回退到上一个已发布版本；无 `client_id` 一律不进入灰度。
- 上线接口 `expected_current_release_id` 缺省视为“期望通道尚无生效版本”（首次上线），此后必须显式传当前指针。

### 15.2 阶段二/三实现补充口径（2026-10-20）

- 回滚接口已实现（4.6）：`expected_current_release_id` **必填**；回滚目标不能是 `draft`；复用上线同一套指针移动事务。
- 强制更新阈值接口已实现（4.7）：`PATCH /v1/admin/apps/{app_id}/channels/{channel}`，审计动作 `update_min_version`。
- 新增 `PATCH /v1/admin/releases/{release_id}`：调整已登记版本的灰度比例 `rollout`（文档 6.1 “比例可随时调整”），审计动作 `update_rollout`。
- 速率限制：Workers ratelimit 绑定，查询 120 次/分（按 `client_id`，缺省按 IP）、下载 30 次/分（按 IP），超限返回 `RATE_LIMITED`；绑定未配置时自动跳过。
- 基础监控：Analytics Engine 数据集 `releasedock_metrics`，记录查询次数与更新可见性、下载次数与字节数，按 `app_id` 聚合；运维指标告警仍依赖 Cloudflare 控制台。
- 客户端更新库已交付（`client/`，零依赖纯 Web API）：查询、下载、SHA-256 校验、进度回调；Node/Electron 另提供流式落盘入口，校验失败自动清理临时文件。
- CI 集成示例见 `.github/workflows/release.yml`：登记自动、上线手动触发（对应 7.2 建议）。
- **新增 `POST /v1/admin/uploads/presign`（上传预签名）**：解决"下游上传更新包还需另外申请 Cloudflare S3 凭据"的体验问题。请求 `{app_id, channel, version, filename, expires_seconds?}`，服务端以 AWS SigV4 签发 path-style 的 R2 预签名 PUT URL（默认 15 分钟），对象键固定为 `{app_id}/{channel}/{version}/{filename}`。下游只需管理 Token 即可完成上传，无需任何 Cloudflare 凭据。
  - 客户端必须**不附加任何自定义头**（`host`、`x-amz-content-sha256` 由 HTTP 栈自动处理，手动设置会造成 `SignatureDoesNotMatch`）。
  - 已被 `live`/`archived` 版本占用的对象键拒绝签发（409 `KEY_ALREADY_LIVE`），登记接口同样拒绝，落实 3.2 节"不覆盖已上线对象"的约束。
  - 服务端需配置 `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`；未配置时返回 503 `UPLOAD_NOT_CONFIGURED`，可回退为 wrangler/S3 工具直传。
  - 大文件（GB 级）建议下游使用 S3 分片上传（boto3/rclone），预签名 PUT 适合单次整包上传。
